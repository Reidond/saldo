# @saldo/api

The API Worker, `saldo-api`: it verifies the owner's Cloudflare Access token and serves `/api`. It has no public route, no workers.dev or Preview URL and no static assets; the web Worker (`saldo-web`) reaches it only over its `API` service binding and forwards the verified `Cf-Access-Jwt-Assertion`, which this Worker verifies again. It runs [Elysia](https://elysiajs.com) 1.4 on its Cloudflare Worker adapter, on D1 for storage.

The layering rules (HTTP → services → repositories, plus `@saldo/domain`) are in [AGENTS.md](../../AGENTS.md#backend-architecture-appsapi). `tests/architecture.test.ts` enforces them.

```text
src/
  worker.ts          composition root: Env bindings → adapters → services → app
  http/              Elysia app, guards, routes, body limit, error mapping
  services/          one class per capability, ports (interfaces) and errors
  repositories/      SQL only: one exported function per statement
  infrastructure/    adapters for service ports: Access JWT verifier, AI providers, clock and ids
migrations/          additive D1 migrations (checked by scripts/ci/migrations.ts)
tests/               see "Tests"
```

## Commands

From the repository root: `pnpm db:migrate` applies the migrations to the local D1 (`cf d1 migrations apply … --local`), `pnpm dev:api` runs `cf dev` on `127.0.0.1:8787`, and `vp run --filter @saldo/api test` runs this package's tests. `pnpm check` runs everything CI runs. The Worker is configured in `cloudflare.config.ts` and built by `cf build` (Vite and the Cloudflare Vite plugin).

`cf dev` evaluates the Worker inside a runner object, where workerd forbids code generation, so `src/http/app.ts` falls back to Elysia's dynamic handlers there. A deployed Worker compiles the app at startup with the Cloudflare adapter, as before.

## HTTP contract

The web client depends on everything in this section. Change it deliberately, and update `tests/http-contract.test.ts` with it.

### Rules for every request

1. **Origin.** A method other than `GET`, `HEAD` or `OPTIONS` needs `Origin` equal to `APP_ORIGIN`. Otherwise the response is `403 {"error":"Origin not allowed"}`, before authentication.
2. **Authentication.** The `Cf-Access-Jwt-Assertion` token must verify against the team's JWKS (`https://<ACCESS_TEAM_DOMAIN>/cdn-cgi/access/certs`). The checks are RS256, issuer `https://<ACCESS_TEAM_DOMAIN>`, audience `ACCESS_AUD`, `exp` and `iat` (5 seconds of clock skew), `type: "app"` (an Access application token), and a subject exactly equal to `OWNER_SUB`. These are the web gate's checks, so both Workers accept exactly the same tokens. If anything is missing or wrong, every path except `/api/status` answers `401 {"error":"Private Saldo instance. Configure Cloudflare Access and sign in as the owner."}`. This includes paths outside `/api/`. Identity headers such as `Cf-Access-Authenticated-User-Email` are ignored.
3. **Login.** The first authenticated `/api/*` request links the Access identity (issuer and subject) to a `users` row. Status checks read the database but never write, and paths outside the API do not touch it. A user whose `status` is `disabled` gets `403 {"error":"This Saldo instance is private."}`. A token issued at or before the user's `sessions_valid_after` gets the 401 above; `POST /api/session/sign-out` sets it. Once an owner exists, a different Access identity (a changed `OWNER_SUB` or team domain) gets the 403 unless the owner opted in to a handover (see "Owner identity handover"). Updating the profile and last-seen time is best effort: if that write fails, the request still succeeds.
4. **JSON responses.** All API responses, errors included, are JSON with `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`.
5. **Errors.** Errors use the shape `{"error": string}`. A request body that cannot be accepted (invalid JSON, schema validation, unavailable storage) gets `400` with `"Invalid data or unavailable storage. No unreviewed changes were saved."`. One exception: review conflicts from `@saldo/domain` keep their own message, for example `"Possible duplicate: <name>. Review as an update instead."`, `"Duplicate subscription ID"`, `"Update target not found"` and `"Repeated or missing review target"`. The rule is any message that contains `duplicate`, `Duplicate` or `target`.
6. **Body limit.** Bodies are JSON (UTF-8) of at most 12,000,000 bytes, checked on `Content-Length` and on the bytes actually streamed. A larger body gets `413 {"error":"Request exceeds upload limit"}`. Bodies are read only after authentication.
7. **Unknown API paths.** For a verified owner, any other `/api/...` path or method gets `404 {"error":"Not found"}`, including `HEAD` on the `GET` routes and trailing slashes. Paths are matched exactly and are case-sensitive.

**Idempotency and request IDs.** The only idempotency key is `requestId` on `/api/review`, which is unique per account. The API reads and sets no request-ID header.

**AI.** `/api/chat` and `aiConnected` use the private `saldo-ai-bridge` service binding (`AI`, with `AI_BRIDGE_SECRET`) through `src/infrastructure/ai/bridge-provider.ts`. Without the binding, the disabled provider makes AI explicitly unavailable. Subscription CRUD and review never depend on AI.

### Known quirks kept for compatibility

These behaviors predate the Elysia rewrite and are pinned by the contract tests. Change them only together with the web client.

- A network error or timeout reaching the AI bridge (as opposed to an error response from it) returns the generic `400`, not `503`.
- Proposals returned by `/api/chat` are schema-checked but not yet checked against the ledger. `/api/review` checks them when they are saved.
- `/api/status` answers every method, while `HEAD` on the other `GET` routes is a `404`.

## Configuration

| Binding or variable                             | Kind                 | Purpose                                                            |
| ----------------------------------------------- | -------------------- | ------------------------------------------------------------------ |
| `DB`                                            | D1                   | Subscriptions, reviews, users and identities.                      |
| `FILES`                                         | R2                   | Reserved for attachments; unused today.                            |
| `AI`                                            | Service, optional    | The private AI bridge.                                             |
| `AI_BRIDGE_SECRET`                              | Secret, optional     | Bearer secret for the bridge.                                      |
| `APP_ORIGIN`                                    | Variable             | The exact HTTPS origin, used for the Origin check.                 |
| `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`, `OWNER_SUB` | Variables or secrets | Access verification. If any is missing, every request is rejected. |
| `OWNER_HANDOVER_FROM`                           | Secret, optional     | Opt-in owner identity handover; unset normally (see below).        |

`migrations/0002_identity.sql` adds `users`, `user_identities` (primary key `provider, issuer, subject`) and `audit_events`. It follows the identity design in the ChatGPT-connect and login plan, with two differences forced by the additive migration grammar: length limits are enforced in code, and the single owner per account is enforced by the identity service rather than a partial unique index. A new owner's `account_id` is their Access subject, which is the key existing rows already use, so no data is rewritten.

### Owner identity handover

An Access identity is the issuer (the team domain) plus the subject. If the owner's subject changes (they were removed and re-added in Zero Trust) or the team domain changes, the new identity is a stranger to Saldo: it gets `403` and never inherits the owner's account by itself. A handover is an explicit owner decision:

1. Change `OWNER_SUB` or `ACCESS_TEAM_DOMAIN` as a release setting ([DEPLOYMENT.md](../../docs/DEPLOYMENT.md#owner-identity-handover)).
2. Set the `OWNER_HANDOVER_FROM` Worker secret to the subject the owner signed in with before (unchanged for a team-domain change).
3. On the first request of the new identity, the identity service links it to the existing owner and account in one batch and records `identity.handover` with `{provider, issuerChanged, subjectChanged}`.
4. Delete the secret.

The handover is accepted only from the owner's most recently linked identity, so a value left behind cannot move the account a second time, and it never revives a disabled or signed-out owner. The previous identity stays linked but can no longer sign in, because it no longer matches the configuration.
